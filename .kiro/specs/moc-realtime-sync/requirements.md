# Requirements Document

## Introduction

本功能旨在实现MOC（Map of Content）笔记的实时同步功能。当用户在MOC索引文件中添加、删除或修改节点时，所有相关的视图（Index View和Graph View）能够自动检测变化并实时更新显示，无需手动刷新。

## Glossary

- **MOC文件**: Map of Content索引笔记，包含思维树结构的Markdown文件
- **Index View**: 主索引视图，显示完整的思维树结构
- **Graph View**: 局部关系视图，显示当前文件的上下文关系
- **节点**: 思维树中的一个条目，对应一个wiki链接和节点ID
- **实时同步**: 文件变化后自动检测并更新视图，延迟小于1秒

## Requirements

### Requirement 1

**User Story:** 作为用户，我希望在MOC文件中添加新节点后，相关视图能自动更新，这样我就不需要手动刷新页面。

#### Acceptance Criteria

1. WHEN 用户在MOC文件中添加新的列表项（包含wiki链接和节点ID）THEN Index View和Graph View应在1秒内自动显示新节点
2. WHEN 新节点添加完成后 THEN 新节点应正确显示其父子关系和层级结构
3. WHEN 多个视图同时打开时 THEN 所有视图应同步更新
4. WHEN 用户正在编辑MOC文件时 THEN 视图更新不应干扰用户的编辑操作

### Requirement 2

**User Story:** 作为用户，我希望删除或修改MOC文件中的节点后，视图能自动反映这些变化，这样我可以实时看到思维树的最新状态。

#### Acceptance Criteria

1. WHEN 用户删除MOC文件中的节点 THEN 该节点应从所有视图中移除
2. WHEN 用户修改节点的ID或链接 THEN 视图应更新显示修改后的内容
3. WHEN 用户修改节点的层级（缩进）THEN 父子关系应正确更新
4. WHEN 修改涉及多个节点时 THEN 所有相关节点的关系应正确重新计算

### Requirement 3

**User Story:** 作为用户，我希望系统能智能地检测文件变化，避免不必要的更新，这样可以保持良好的性能。

#### Acceptance Criteria

1. WHEN MOC文件内容未实际改变时 THEN 系统不应触发视图更新
2. WHEN 用户快速连续编辑时 THEN 系统应使用防抖机制，避免频繁更新
3. WHEN 多个MOC文件同时变化时 THEN 系统应只更新当前显示的MOC相关视图
4. WHEN 非MOC文件变化时 THEN 系统不应触发MOC视图的更新

### Requirement 4

**User Story:** 作为用户，我希望在视图更新时能看到清晰的反馈，这样我知道系统正在处理我的更改。

#### Acceptance Criteria

1. WHEN 检测到文件变化时 THEN 系统应显示加载指示器或过渡动画
2. WHEN 更新完成后 THEN 系统应平滑地显示新内容，避免闪烁
3. WHEN 更新失败时 THEN 系统应显示错误提示并保持当前视图状态
4. WHEN 大量节点变化时 THEN 系统应显示进度提示

### Requirement 5

**User Story:** 作为开发者，我希望系统架构清晰且易于维护，这样未来可以方便地扩展功能。

#### Acceptance Criteria

1. WHEN 实现文件监听时 THEN 应使用Obsidian提供的标准API
2. WHEN 处理视图更新时 THEN 应遵循单一职责原则，分离监听、解析和渲染逻辑
3. WHEN 添加新的视图类型时 THEN 应能轻松集成到现有的同步机制中
4. WHEN 系统出现错误时 THEN 应有完善的错误处理和日志记录

## 实现方案对比

### 方案1: 基于Obsidian Vault事件的轮询检测

**原理**: 监听Obsidian的`vault.on('modify')`事件，当MOC文件被修改时触发更新。

**优点**:
- 实现简单，使用Obsidian原生API
- 可靠性高，不会遗漏文件变化
- 与现有代码集成容易

**缺点**:
- 每次保存都会触发，可能过于频繁
- 无法区分实质性变化和格式变化
- 用户编辑时可能频繁触发

**性能**: ⭐⭐⭐⭐ (良好)
**实现难度**: ⭐⭐ (简单)
**推荐指数**: ⭐⭐⭐⭐

### 方案2: 基于内容哈希的智能检测

**原理**: 在方案1基础上，计算MOC文件相关内容的哈希值，只有哈希变化时才更新视图。

**优点**:
- 避免不必要的更新，性能更好
- 可以精确检测实质性变化
- 用户体验更流畅

**缺点**:
- 需要额外的哈希计算开销
- 实现复杂度增加
- 需要维护哈希缓存

**性能**: ⭐⭐⭐⭐⭐ (优秀)
**实现难度**: ⭐⭐⭐ (中等)
**推荐指数**: ⭐⭐⭐⭐⭐

### 方案3: 基于防抖的延迟更新

**原理**: 使用防抖机制，在文件修改后等待一段时间（如500ms）再更新，避免频繁触发。

**优点**:
- 减少更新频率，性能好
- 实现相对简单
- 适合快速连续编辑的场景

**缺点**:
- 有延迟感，不是真正的"实时"
- 可能错过中间状态
- 延迟时间难以平衡

**性能**: ⭐⭐⭐⭐⭐ (优秀)
**实现难度**: ⭐⭐ (简单)
**推荐指数**: ⭐⭐⭐⭐

### 方案4: 基于增量更新的差异检测

**原理**: 解析文件变化，计算新旧内容的差异，只更新变化的节点。

**优点**:
- 最优性能，只更新必要部分
- 视图更新平滑，无闪烁
- 可以实现动画过渡效果

**缺点**:
- 实现复杂度最高
- 需要维护完整的状态树
- 差异算法可能有bug

**性能**: ⭐⭐⭐⭐⭐ (优秀)
**实现难度**: ⭐⭐⭐⭐⭐ (困难)
**推荐指数**: ⭐⭐⭐

### 方案5: 混合方案（推荐）

**原理**: 结合方案2和方案3，使用内容哈希检测 + 防抖机制。

**优点**:
- 平衡性能和实现难度
- 避免不必要的更新
- 用户体验好
- 易于维护和扩展

**缺点**:
- 需要同时实现两种机制
- 略微增加代码复杂度

**性能**: ⭐⭐⭐⭐⭐ (优秀)
**实现难度**: ⭐⭐⭐ (中等)
**推荐指数**: ⭐⭐⭐⭐⭐

## 推荐实现方案

**采用方案5（混合方案）** - 用户无感知 + 性能优秀

基于用户需求（体验好、无感知、性能好），混合方案是最佳选择：

### 为什么选择混合方案？

1. **用户无感知**：
   - 防抖机制确保编辑时不会频繁闪烁
   - 哈希检测避免无意义的视图重绘
   - 更新延迟控制在300-500ms，用户几乎感觉不到

2. **性能优秀**：
   - 只在内容真正改变时才更新（哈希检测）
   - 避免快速连续编辑时的重复计算（防抖）
   - 内存占用小，只缓存哈希值

3. **实现可行**：
   - 中等难度，可分阶段实施
   - 代码清晰，易于维护
   - 可以逐步优化

### 具体实现策略

**阶段1: 基础防抖（1-2天）**
- 实现文件监听
- 添加500ms防抖
- 基本的视图刷新

**阶段2: 哈希优化（1天）**
- 添加内容哈希计算
- 缓存机制
- 智能跳过无变化更新

**阶段3: 体验优化（1天）**
- 加载指示器
- 平滑过渡动画
- 错误处理

### 性能指标

- **更新延迟**: < 500ms
- **CPU占用**: < 5%（空闲时）
- **内存增加**: < 10MB
- **用户感知**: 几乎无感知

### 与其他方案对比

| 指标 | 方案2(哈希) | 方案3(防抖) | 方案5(混合) |
|------|------------|------------|------------|
| 用户无感知 | ⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |

**结论**: 方案5在用户体验和性能之间达到最佳平衡，完全符合"用户无感知 + 性能较好"的要求。

## 技术实现要点

### 文件监听
```typescript
// 监听MOC文件夹中的文件变化
this.registerEvent(
    this.app.vault.on('modify', async (file) => {
        if (this.isMOCFile(file)) {
            await this.handleMOCFileChange(file);
        }
    })
);
```

### 防抖机制
```typescript
private debounceUpdate = debounce(async (file: TFile) => {
    await this.updateViews(file);
}, 500);
```

### 哈希检测
```typescript
private async hasContentChanged(file: TFile): Promise<boolean> {
    const content = await this.app.vault.read(file);
    const newHash = this.calculateHash(content);
    const oldHash = this.contentHashCache.get(file.path);
    
    if (newHash !== oldHash) {
        this.contentHashCache.set(file.path, newHash);
        return true;
    }
    return false;
}
```
