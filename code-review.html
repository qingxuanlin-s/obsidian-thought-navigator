02

做对的事

CREDIT WHERE DUE
SAFE 01 ─ 数据流

单一突变入口

所有 MOC 修改都走 MOCHandler.modifyMOCData() —— 深拷贝 → 回调 → 序列化 → 写盘。 这种"漏斗"结构让数据流可推理:任何 bug 都能在一个函数边界内复现。 这是整个项目最值钱的设计决策。

SAFE 02 ─ 存储格式

Mermaid 即可视化

把 MOC 存成 ```mermaid 代码块 —— Obsidian 原生渲染、GitHub 直接看图、纯文本可 diff。 文件本身就是它的"预览图",这是真正聪明的设计妥协。

SAFE 03 ─ 性能

反向索引 + 增量更新

notePath → MOCLocation[] 内存索引让 "这条笔记出现在哪些 MOC"是 O(1) 查询。 增量更新而非全量重建 —— 扩展性可以撑得住。

SAFE 04 ─ 解耦

View 之间用事件交流

五个 ItemView 通过 refresh-local-graph 等命名事件交互, 不持有彼此引用。Obsidian 风格,符合直觉, 未来加新 view 不会导致级联修改。

锐评。

UNVARNISHED
01
严重

CytoscapeRenderer.ts 是核反应堆级别的 God Class

12,739 行 / 618 个方法签名 / 占代码库 38% —— 你已经触碰了人类记忆无法容纳单文件的天花板。

继续在这个文件里改任何东西,本质都是"我希望我没有破坏什么"的赌博。 它至少应该被劈成 6–8 个文件: events · layout-adapter · embed-preview · edge-controls · overlay-drag · embed-card-cache · inline-editor。

不重构,后面每加一个功能都会越来越慢。
02
严重

0 测试 + 33K 行 = 倒计时炸弹

解析器 + 序列化器 + 撤销 + 缓存 + 增量布局 + 跨域链接 —— 这些都是"你以为它好了,直到下次重构才发现它一直坏"的典型模块。

MermaidParser.clearCacheForFile() 那个同秒写入 mtime 缓存命中陈旧值的坑, 就是个早期警告 —— 你已经在裸奔时被绊过一次了。

最高 ROI 的一项投入:写 parse → serialize → parse 等价测试。一周内能搞出来,十年内会持续救命。
03
中

%% ext:{JSON} %% 是穿着注释外衣的并行数据库

你用一个看似"附属注释"的字段,塞进了 节点位置 / 颜色 / 分组 / 边曲率 / 嵌入尺寸 / 备注 / 布局风格 —— 这已经远超"元数据"的体量,是一个完整的状态文件。

它寄生在 Mermaid 块尾巴上,随时可能被外部编辑器手抖删掉, 没有 schema 版本,没有合并冲突的语义。中间态最危险。

两条路选一条:① ext 移到 sidecar `.moc.json`;② 全量 JSON,Mermaid 降级为渲染产物。
04
中

三个布局引擎 = 选择困难症的具象化

dagre + cose-bilkent + elkjs + d3 + 又重复出现的 dagre。 为了"灵活性"你付出了:bundle 体积、布局结果不一致、用户教学成本。

Obsidian 插件体积是有口碑成本的, "isDesktopOnly": false 还得考虑移动端 —— 这套依赖在 iPad 上加载会很难看。

挑一个做主力(我赌 ELK),其他做实验性 opt-in,别都默认进 bundle。
05
中

Undo 在内存里,且只有 7 步

重启 Obsidian 一次,撤销栈清零。 深度 7 在长操作会话里几乎注定触底 —— 用户改了 8 个节点想撤销到一开始,会发现回不去了。

且存的是原始文件全文而不是 patch,内存压力还不小。

持久化到 IndexedDB,深度提到 30,改存 patch。这是"用户感知"层面 ROI 最高的改动。
06
轻

ID 命名有三套互不相通的体系

cd-xxx(跨域) · placeholder-xxx(占位) · free.1(自由节点) · a.1.b(常规 Luhmann)。 每加一种特殊节点就再发明一个 ID 前缀,字符串解析散布在多处。

类型系统能帮你管住: type NodeId = LuhmannId | FreeId | CrossDomainId | PlaceholderId。

下次因为前缀字符串拼错而调试半小时,你会想起这条。
07
轻

ext JSON 没有 schemaVersion

当你下次给 ext 加字段,旧版本插件遇到新文件会怎么处理? 新版本插件遇到旧文件会怎么处理?目前都是"祈祷一下不出事"。

一个 schemaVersion: 2 字段 + 一个 noop 迁移函数, 就是 5 行代码换十年安心。

现在加便宜,等用户数据散落出去之后再加,代价指数级上升。
08
观察

0 个 TODO / FIXME 注释 —— 这反而可疑

要么你是宇宙级自律的开发者, 要么"已知不完美但还没空修"的部分都散落在你脑子里 —— 脑子里的 TODO 会忘。

建议建立一个 docs/known-issues.md 或允许在代码里写 // TODO(name): ...。当你从这个项目离开三个月再回来, 你会感谢那时候肯写下来的自己。

代码注释不是污渍 —— 在合适的地方,它们是给未来的你的便利贴。

Quick Wins · 先做

低成本、高影响。round-trip 测试 1 周内能搭起来,后续每次重构都会回报你。

Big Bets · 排进 roadmap

需要一个完整 release cycle。拆分 CytoscapeRenderer 是其中最痛但最值的。

Fillers · 顺手做

没人催但写起来轻松。等你需要 context-switch 休息一下时去做。

Question Marks · 暂缓

大投入、不确定回报。在以上事项做完前不应启动。
